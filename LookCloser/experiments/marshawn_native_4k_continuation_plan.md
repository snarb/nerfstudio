# Marshawn native mixed-resolution continuation: feasibility and parity plan

## What was tested

Prepare a separate continuation using the existing63 real3840×2024 TRAIN images and unchanged three1920×1012 EVAL images. No training or source mutation is authorized by this document. The current native HD continuation remains active and unchanged. The eventual source checkpoint is the best completed native checkpoint selected at release time, with its exact optimizer, scheduler, scaler, RNG, dynamic-batch and native-core sidecars; it is not fixed prematurely to20k or30k.

Source: `/fsx/tmp/marshawn_001660_hd/tuning_20261106/resolution_4k_train63/`. Proposal evidence: `native_semantic_grid_20000/native_4k_continuation_plan/` in the same campaign. Existing `complete.json` remains `training_eligible=false` and `maps_fitted=false`; it is not edited. A native-specific release would rely on separately reviewed RGB/calibration bindings and needs no LookCloser frequency maps or actor-confidence objective.

## Results

All66 prepared camera rows were checked against the original native dataset. Applying `floor_to_native = inverse(world_to_box)` to the prepared floor-frame poses recovers original native-world camera matrices with maximum absolute error2.22e-16. The proposed metadata then uses the original stored native matrices exactly, avoiding even this roundtrip difference. All63 TRAIN widths, heights, focal lengths and principal points equal exactly twice their HD values; EVAL remains unchanged. All output distortion coefficients remain zero because the images are already undistorted.

The actual frozen native parser was exercised with CUDA hidden and no image cache/model construction. It returns63 TRAIN and3 EVAL cameras, exactly equal native pose tensors, unchanged scene AABB and normalization, and exactly equal corresponding continuous-center ray origins/directions for every camera. The first attempt imported the full TrainerConfig, which initialized a tinycudann CUDA context; its no-GPU assertion was rejected and the successful parser-only check explicitly avoids that import. No optimizer or model was constructed in either attempt.

Per-camera original HD, prepared4K and proposed native-world rows, RGB/valid-mask hashes, RAW TIFF lineage and every RAW OPENCV calibration are bound in `source_parity.json` and `raw_calibration_and_geometry_bindings.json`. All66 original native HD RGB and valid-mask files also match the current campaign files exactly. The existing4K exporter independently replayed all63 HD conversions byte-for-byte, and its504 array checks passed.

The spatial conversion remains: vendor Log3G10/RWG decode to positive linear Rec709, linear AREA prefilter at target resolution, one calibrated lens remap, the same fixed gain4 and TRAIN-fitted radialK4/scalar correction, then Reinhard+sRGB8. RAW calibration is8192×4320 OPENCV; OpenCV array coordinates use principal-point minus.5. For a corresponding HD array coordinate `u`, the4K array coordinate is `2*(u+.5)-.5`; corresponding continuous centers scale by2. Integer4K pixels intentionally add different subpixel rays. There is no new calibration, exposure fit or white balance.

The frozen VanillaDataManager calls `InputDataset.__getitem__`, whose default image type is float32. Its config's `cache_images_type='uint8'` does not make this cache uint8. Keep this behavior for the controlled comparison; changing cache dtype would require a separate exact-value/RNG test. The host has about30GiB RAM. The current HD producer uses roughly4.4GiB resident RAM and no process swap, with other system swap already in use. A full4K cache probe should run after the HD producer releases its GPU/cache or under a separately reviewed memory budget. Peak startup needs the collation estimate plus model, optimizer, Python, geometry arrays and allocator overhead; do not assume the final5.5GiB cache is the peak.

## Proposed implementation and strict checks

The frozen constructor cannot simply be pointed at4K. `FinalNativePipeline` hash-binds the old RGB directory/transforms, and both SfM and MVS objectives validate the original HD transforms. Those checks are valuable and must not be bypassed.

An isolated adapter has now been staged under `adapter/code/`. It changes only constructor validation/binding paths in copied historical `marshawn_final_pipeline.py` and `marshawn_mvs_distribution_candidate.py`, adding an explicit native-camera/resolution validator. All nonconstructor training, sampling, objective and grid methods are AST-identical to the historical sources. The original helpers and active producer remain unchanged.

CPU checks pass for HD identity and4K bindings, and reject five deliberate errors: changed native pose, wrong focal length, changed EVAL dimensions, reordered camera split, and wrong geometry hash. Original/staged SfM and surface buffers match exactly, and private sampling IDs/points match at steps20k,30k,35k and100k. The original/staged MVS constructors also produce exactly equal world arrays and private sample choices on CPU. The full native pipeline, prior outputs/gradients and optimizer restart still require the reviewed GPU gate; these CPU checks do not substitute for it.

Concrete `HD_identity_config_NOT_RELEASED.yml`, `TRAIN4K_config_NOT_RELEASED.yml` and `technical_probe_spec.json` are staged. Both RGB gates deliberately remain `approved=false`, both checkpoint paths remain unmaterialized, and technical/production authorization flags remain false. The current source selection is only a planning snapshot; materialization must refresh it after HD completion and bind its exact checkpoint/runtime/core/metrics. The probe specification splits32 attempted updates around a save/reload at16, records actual Adam changes and AMP skips separately, and excludes probe checkpoints from production ancestry.

## Scientific scope and limitations

The intended treatment is one bundled factor: TRAIN spatial resolution and its corresponding RAW prefilter/ray lattice. Model capacity, SH/color architecture, geometry priors, native normalization/occupancy, actor weighting, optimizer schedule and common FHD evaluation stay fixed.4K carries less spatial averaging, so it can expose both real detail and sensor/compression/calibration noise. The source conversion preserves the photometric recipe, but tone mapping and resampling do not commute; a resized4K PNG is not expected to reproduce the independently rebuilt HD PNG exactly. Same-step sampling covers each4K pixel less often, and unchanged FHD validation may understate a truly4K-only improvement.

Warm continuation alone also adds optimization time. To attribute a gain to resolution, compare matched additional-step HD and4K branches from the same complete checkpoint. Reuse the existing HD trajectory after that exact checkpoint where available; otherwise a separately reviewed HD control is needed. The current geometry-supervised HD reference remains the scientific comparator, not the LookCloser architecture-only arm. No improvement, high-resolution generalization, or artifact-free claim is supported before those checks and visual evaluation.
